# AI-buddy: спецификация сценария и поведения

## Путь стажёра и границы

В первую неделю стажёр знакомится с командой и инструментами, получает доступ для первой рабочей задачи. Основной сценарий прототипа — ошибка Jira 403 и заявка на чтение проекта BUD. Пока заявка рассматривается, стажёр может изучать чек-лист и материалы команды. Во вторую неделю фиксирует цели и задачи вместе с наставником. [Чек-лист из кейса](https://docs.google.com/spreadsheets/d/1qKFqOzfSZ2jEz57jBSmq7rukDXi_tRfWohgemViceV0/edit)

BUD и рабочие инструкции команд — синтетический пример, помеченный `demo`. Проект показывает один законченный процесс, без обещания управлять всем онбордингом или выдавать реальный доступ.

## Поведение

| Условие | Ожидаемое действие | Проверяемый результат |
| --- | --- | --- |
| Приветствие или вопрос о возможностях | Локальное представление, примеры поддерживаемых вопросов | `conversation`, нет вызова поиска и LLM, нет выдуманных цитат |
| Короткая неопределённая проблема | Уточнение инструмента и ошибки | `conversation`, нет случайных инструкций |
| Приветствие с рабочим вопросом | Обработка рабочего вопроса | Jira 403 не теряется за словом «Привет» |
| Вопрос о Jira 403 от стажёра Platform | Поиск подходящей разрешённой инструкции, ответ по источникам | Предложение `preview_jira_access`, самостоятельного действия нет |
| Уточнение «А к какому проекту?» | Ограниченная история помогает сформировать запрос и ответ | Ответ про BUD со ссылкой на текущую инструкцию |
| Новый явно названный рабочий вопрос | Поисковый запрос не дополняется старой темой | Предыдущий разговор про ревью не мешает вопросу про Jira |
| В найденном наборе есть посторонние правила | Отбор по теме перед проверкой конфликтов | Правила ревью/просроченный dev не блокируют Jira |
| Разрешённые инструкции по ревью противоречат друг другу | Показ обеих формулировок и обращение к наставнику | `conflict`, обе ссылки, нет произвольного победителя |
| Единственный подходящий документ просрочен | Дата и рекомендация уточнить порядок | `needs_review`, документ не выдаётся за действующую процедуру |
| Нет доступных доказательств | Объяснение отсутствия ответа, эскалация | `insufficient_evidence`, скрытый документ не раскрывается |
| Роль/команда не разрешает документ | Исключение до передачи модели | Недоступный текст не попадает в ответ или контекст провайдера |
| Сбой поиска или LLM | Безопасный код конкретного класса ошибки | Ручной повтор, интерфейс отзывчив, ошибка сохраняется |
| Внешняя генерация не работает | Явный запрос пользователя на выдержку | Поиск выполняется отдельно; ответ есть только при подходящей инструкции |

## Хранение и интеграции

Браузер вызывает Go REST через Caddy. Go определяет роль и команду, сохраняет pending-запрос в PostgreSQL и вызывает Python по gRPC. Python REST остаётся внутренним. Результат или безопасная ошибка записываются в диалог. Повтор с тем же idempotency key возвращает прежний результат. Сервер завершает начатую генерацию в ограниченном контексте даже после закрытия страницы; зависший после перезапуска pending-запрос истекает и становится ошибкой.

В LLM передаются до трёх завершённых пар сообщений, максимум 8000 символов суммарно; отдельные вопросы и ответы обрезаются до 2000 символов. История служит недоверенным контекстом, не доказательством фактов и не источником полномочий. Текущие документы по-прежнему нужны для рабочих инструкций. Новый диалог закрывает предыдущий; просмотр архива не реализован.

Предложение действия открывает форму. Go проверяет параметры и права при подготовке и подтверждении, вызывает mock-сервис, сохраняет и показывает номер и статус. `pending` означает «На согласовании», а не выданный доступ. Повтор не создаёт дубликат. Запрос статуса и фоновая сверка обновляют существующую заявку. Переходы `granted`/`rejected` отражаются в следующем шаге.

CLI содержит отдельную тестовую имитацию действия. Для основного GUI-сценария источником истины по заявкам служит Go API, а не текст модели и не CLI-таблица RAG.

## Поиск и модель

Рабочее хранилище — PostgreSQL/pgvector. Документы индексируются локальной `BAAI/bge-m3`, 1024 измерения; запрос сравнивается по косинусной близости. Доступ и текущая публикация фильтруются SQL до top-k. Противоречащие варианты размеченного правила добавляются в том же снимке. SQLite FTS остаётся изолированным стендом части тестов/evals и не является рабочим поиском приложения.

Доступные фрагменты дополнительно ограничиваются темой явно названного инструмента или процесса перед проверками конфликта и срока. Для небольшого учебного корпуса используется компактный набор тем; универсальная тематическая классификация и reranker не заявлены. Отсутствие keyword-совпадения вне известных тем само по себе не отключает семантический поиск.

По умолчанию генерация использует фиксированную `nvidia/nemotron-3.5-lightning:free` через OpenRouter с `RAG_LLM_REASONING=off`. Можно настроить модель и базовый URL через env. Для другой модели необходимо проверить поддержку reasoning; `default` оставляет настройки провайдеру. Система сохраняет имя фактически ответившей модели, измеряет время поиска и генерации и различает ошибки без журналирования текстов и ключей. Автоматических повторов или перехода на платную модель нет.

Общий RPC-бюджет — 60 секунд, внешняя генерация ограничена 25 секундами и оставшимся бюджетом. Ожидание браузера — 70 секунд, HTTP-запись Go — 75 секунд; orphaned pending истекает через 120 секунд. Для короткого уточнения поиск повторно использует предыдущий содержательный вопрос; сама уточняющая реплика и история передаются LLM. Локальная модель использует ограничение потоков в Compose, повторные embeddings кешируются ограниченно в памяти процесса; проверки прав всегда выполняются повторно в SQL. Векторный кеш не заменяет хранение переписки. Доступность бесплатного провайдера и качество произвольных вопросов не гарантируются.

## Качество, безопасность и проверки

[Guardrails](rag-guardrails.md) ограничивают структуру и объём ответа, ссылки, активное содержимое и заявления о выполненных действиях. Это не полноценная проверка истинности или защита от всех prompt injection. Операции исполняет Go с отдельной проверкой прав и подтверждением пользователя.

Проверки включают общий разговор без поиска, смешанные реплики, релевантность Jira, реальные конфликты, источники, ACL, историю, ошибки провайдера и восстановление. PostgreSQL-тесты используют отдельные временные базы и фиксированные векторы. [30 offline evals](../rag/evals/README.md) проверяют fixture-поиск и границы, не измеряют качество BGE или реальной LLM. Сквозной запуск с реальными embeddings и моделью проверяется отдельно. [Покрытие строк всего приложения](COVERAGE.md).

## Польза и пилот

Предложенные метрики: доля самостоятельных корректных заявок, медианное время от 403 до номера заявки, количество обращений к наставнику, доля подтверждённых источниками ответов и число ошибок/дубликатов.

Для пилота дать сопоставимым группам одну синтетическую задачу: одной — обычные инструкции, другой — AI-buddy. Зафиксировать условия, число участников и критерий успеха. При повторном участии учитывать обучение и менять порядок вариантов. Настоящие конфликты учитывать отдельно от повторных вопросов с доступным ответом. Прохождение демо и тестов не доказывает экономию часов наставника.
