# Поведение AI-buddy при выполнении первой задачи

## Путь стажёра

В первую неделю стажёр знакомится с командой, наставником и рабочими инструментами. Он запрашивает доступ к проекту для первой задачи. Пока заявка рассматривается, стажёр может выполнять доступные пункты чек-листа. Во вторую неделю он фиксирует цели и изучает материалы команды. Доступ к Jira проекта BUD и инструкции Platform в демонстрации синтетические. [Чек-лист из кейса](https://docs.google.com/spreadsheets/d/1qKFqOzfSZ2jEz57jBSmq7rukDXi_tRfWohgemViceV0/edit)

| Условие | Поведение | Проверяемый результат |
|---|---|---|
| Стажёр Platform сообщает о 403 в Jira | Поиск ограничивает источники ролью и командой. Помощник показывает подтверждённый источником следующий шаг. | Доступна инструкция на чтение проекта BUD. |
| Стажёр открывает заявку | Адаптер проверяет профиль и действующую инструкцию, показывает систему, проект, уровень доступа и обоснование. | Статус `draft`, число сохранённых заявок не меняется. |
| Стажёр подтверждает данные | Адаптер повторно проверяет право на операцию и правило в одной транзакции с записью. | Номер заявки и статус `pending` сохранены. Согласование выполняет владелец проекта. |
| Двойное подтверждение или повторный запуск | Уникальный ключ состоит из сотрудника, проекта и уровня прав. | Стажёр получает прежний номер. |
| Роль или команда не разрешают операцию | Адаптер проверяет полномочия независимо от текста запроса и ответа модели. | Операция завершается без создания заявки. |
| Инструкции расходятся | При разных значениях одного размеченного правила помощник приводит обе доступные формулировки и направляет к наставнику. | `conflict`, обе ссылки присутствуют даже при `top_k=1`. |
| Найден только документ с истёкшим сроком проверки | Помощник показывает дату и советует уточнить процедуру у наставника. | `needs_review`, инструкция не выдаётся как действующая. |
| Доказательств недостаточно | Помощник предлагает обратиться к наставнику, затем к руководителю, по кадровым вопросам — к HRBP. | `insufficient_evidence`. Закрытый и отсутствующий документ дают одинаковое сообщение. |
| Провайдер недоступен, ответ оборван или содержит неизвестную ссылку | Клиент возвращает ошибку. Пользователь может повторить вопрос или открыть офлайн-выдержку. | Недостоверный результат не отображается как успешное действие. |

## Поиск и генерация

Единица доступа — документ, единица цитирования — фрагмент конкретной версии. Импорт сначала читает все источники, затем одной транзакцией публикует согласованный снимок. Поиск и проверка связанных правил также читают один снимок. Закрытые и снятые с публикации фрагменты исключаются до отбора контекста. Страница PDF и смещения внутри извлечённого текста позволяют проверить цитату. Ссылки на документы и пометки об их происхождении берутся из манифеста.

Для небольшого демонстрационного корпуса выбран SQLite FTS5. Нормализация связывает русские названия с Jira, Bitbucket, PR и другими терминами. Из доступных кандидатов сохраняются совпадения по большинству содержательных терминов вопроса. Сначала учитывается количество совпадений, затем BM25 с усиленным весом заголовка. Связанные противоречащие правила добавляются к результату. Такой поиск работает на CPU без скачивания весов. Перефразировки без общих терминов или известного синонима могут остаться без ответа. Подключение векторного поиска стоит оценивать на размеченных вопросах из расширенного корпуса.

В онлайн-режиме модель получает роль, команду, вопрос и ограниченный контекст. Клиент отклоняет ссылки на фрагменты вне переданного набора. Проверка ссылок подтверждает их существование, а смысловую точность ответа оценивают на размеченных примерах. Конфликты в свободном тексте без пары `rule_key`/`rule_value` может заметить модель. Офлайн-проверка сопоставляет размеченные правила, а ответ показывает лучшую выдержку. Электронная заявка создаётся только обработчиком подтверждения. При подключении к корпоративному сервису тестовый адаптер заменяется клиентом API, полномочия поступают из авторизованной сессии.

## Проверка пользы

Для пилота дать сопоставимым группам стажёров одну задачу с закрытой доской Jira. В одной группе доступны обычные инструкции, в другой дополнительно доступен AI-buddy. Заранее определить успех как самостоятельную подачу корректной заявки на чтение своего проекта. Сравнить долю успешных попыток, медианное время от 403 до номера заявки и число обращений к наставнику. Уточнения при реальном конфликте помечать отдельно от повторных вопросов с доступным ответом.

Для качества поиска в [тестах поискового конвейера](../rag/tests/test_pipeline.py) зафиксированы ожидаемые источники и вопросы без ответа. На расширенном наборе измерять долю правильных первых источников, ложные ответы при нехватке данных и долю выдач с чужими документами. Время поиска и ожидания провайдера измерять отдельно. Результаты тестового набора и локальная задержка характеризуют прототип. Эффект на стажёрах требует пилота.
