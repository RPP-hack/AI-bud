# AI-buddy: проблемы, приоритеты и соответствие требованиям

Дата сверки: 16 ноября 2026. Ветка: `backend-branch`.

Это список известных проблем и проверок готовности, без расписания и оценок трудозатрат. Цель — работающий продукт с законченным пользовательским сценарием. Незакрытая косметическая задача не должна мешать сдаче.

## Статус реализации

Технические исправления P0–P1 и согласованные изменения GUI реализованы: фиксированная модель, локальные общие реплики, тематический отбор, классификация ошибок, восстановление подключения, скрытые настройки и демонстрационные профили. Воспроизводимый прогон и покрытие: [COVERAGE.md](COVERAGE.md), [отчёт](coverage/SUMMARY.md). Внешняя бесплатная LLM остаётся зависимостью с возможными лимитами; автоматического платного fallback нет.

Добавлена [продуктовая PDF-презентация](../output/pdf/AI-buddy-product.pdf) со ссылками на репозиторий и предоставленную пользователем видеодемонстрацию. Права доступа к видео и загрузку комплекта на платформу команда проверяет отдельно. Исторические наблюдения ниже описывают причины изменений; актуальное поведение зафиксировано в README и SDD.

## Как читать приоритеты

- **P0 — блокирует сдачу:** основной сценарий нельзя пройти, проект нельзя запустить по инструкции или отсутствует обязательная для допуска презентация.
- **P1 — реальная проблема:** нарушает поведение продукта либо оставляет существенный пробел в требованиях. Исправляем или явно подтверждаем выполнение.
- **P2 — желательно:** повышает понятность и удобство; допустимо оставить как ограничение рабочего прототипа.
- **Позже:** расширение продукта, которое не требуется для выбранного сценария.

Приоритеты назначены командой в этом документе, а не организаторами. Требование кейса, подтверждённая ошибка и гипотеза о причине — разные вещи. Наличие тестов или описания функции не доказывает её стабильность в сдаваемой версии.

## Что считаем рабочим продуктом

Основной сценарий: стажёр Platform сообщает об ошибке Jira 403 → получает подходящую инструкцию → открывает и проверяет предложение заявки → явно подтверждает отправку → видит сохранённые номер и статус от mock-сервиса → понимает следующий шаг.

Чат восстанавливается после обновления страницы и перехода в заявки. Продолжение «А к какому проекту?» понимается по истории. Смена профиля не раскрывает чужие данные.

Для первого входа помощник умеет представиться и объяснить, с чем помогает. Полноценный универсальный собеседник для этого не нужен.

## P1: поведение разговора и источники

- [x] «Привет» → представление и примеры реально поддерживаемых вопросов, без тяжёлого поиска.
- [x] «Что ты умеешь?» → объяснение возможностей без обещания выдать реальный корпоративный доступ.
- [x] «Не работает» → уточнение системы, ошибки или цели пользователя.
- [x] «Спасибо, помогло» → короткая реплика без выдачи случайных документов.
- [x] «Привет, Jira выдаёт 403» → обработка рабочего вопроса, а не только приветствия.
- [x] «А к какому проекту?» → использование сохранённой истории и подходящей инструкции.
- [x] Вопрос про Jira не блокируется конфликтом правил про ревью PR.
- [x] Просроченный документ не добавляется в ответ, если он не относится к вопросу.
- [x] На настоящий вопрос о ревью сохраняется показ противоречащих правил с источниками; помощник не выбирает одну сторону без основания.
- [x] При недостатке подтверждённых данных помощник уточняет вопрос или объясняет отсутствие ответа.

Минимальный подход: небольшая обработка общих реплик в существующем RAG-сервисе и отбор подходящих источников. Общие реплики могут обходиться без цитат; рабочие инструкции должны подтверждаться документами. Согласовать это с форматом API и отображением фронтенда.

Не нужны отдельная агентная архитектура, дополнительный LLM-вызов для классификации каждого сообщения или удаление конфликтующих документов ради красивой выдачи.

## P1: выбор модели, задержки и ошибки

### Наблюдения до исправлений

До исправления модель задавалась как `openrouter/free`; OpenRouter выбирает конкретную бесплатную модель. Запрос идёт без `reasoning`, с `stream=false` и `max_tokens=1500`.

Reasoning-модель может расходовать время и бюджет токенов до завершения ответа. Это возможная причина, а не установленный диагноз конкретного сбоя. Скрытие рассуждений через `reasoning.exclude=true` не отключает вычисления.

Общий лимит RAG-запроса — 30 секунд. В предыдущих замерах локальный поиск BAAI/bge-m3 на CPU занимал 10–18 секунд; на генерацию остаётся остаток общего бюджета, максимум 25 секунд. Поэтому замена внешней модели может решить только часть проблемы. Вычисление embedding также не прерывается мгновенно по таймауту.

В интерфейс передаётся настроенное имя модели, а фактически выбранная модель из ответа провайдера не сохраняется. Успешные сквозные ответы занимали около 20–22 секунд. Отдельные сбои не доказывают, что весь процесс падает.

### Минимальные исправления

- [x] Зафиксировать конкретную модель и проверить последовательные запросы по основному сценарию. Фиксация — способ повысить воспроизводимость, а не самостоятельное требование регламента.
- [x] Для выбранной модели проверить поддержку отключения или ограничения reasoning. Не отправлять неподдерживаемые настройки и не считать отключение гарантией скорости.
- [x] Сохранять фактическое имя модели; измерять отдельно поиск и обращение к LLM.
- [x] Различать в диагностике таймаут, ошибку поиска, HTTP-ошибку/лимит провайдера, незавершённый ответ и неправильный формат ответа. Не записывать ключи и содержимое переписки в логи.
- [x] Показывать пользователю понятную причину и ручной повтор; следующая попытка после сбоя должна обрабатываться.
- [x] Проверить доступные настройки локального поиска по результатам замеров. Не менять embedding-модель и не перестраивать весь поиск без необходимости.
- [x] Менять таймауты только согласованно между Go, Python и клиентом, если это подтверждено измерениями.

Полезные дополнительные метрики токенов и streaming — P2. Для рабочего продукта достаточно понимать причину ошибки и стабильно проходить основной сценарий; полный мониторинг и гарантированно мгновенные ответы не требуются.

## P2: настройки интерфейса и профили

- [x] Убрать «Количество источников» из пользовательского интерфейса; оставить лимит поиска на сервере. Это количество первоначально отбираемых фрагментов, а не обязательное число ссылок в ответе. Параметр не нужен стажёру для решения задачи.
- [x] Сделать ответ модели основным режимом. Переключатель «Офлайн / С моделью» убрать из обычного потока либо объяснить его понятным названием.
- [x] При неудаче генерации предлагать «Показать найденную инструкцию», если есть подходящий результат поиска. При недоступности самого поиска обещать такую инструкцию нельзя. Допустим явный повтор поиска с ограниченным ожиданием.
- [x] Переименовать переключатель в «Демо-профиль». При желании оставить в GUI три профиля, сохранив остальные тестовые учётные записи на сервере.

Офлайн сейчас означает локальный поиск и показ выдержки без внешней генеративной модели. Нужны сервер, БД и embedding-модель; это не работа браузера без интернета и не гарантия быстрого ответа.

| Профиль | Для чего нужен |
| --- | --- |
| Стажёр Platform | Общие материалы и материалы Platform; основной сценарий заявки на чтение Jira BUD |
| Стажёр Search | Общие материалы и материалы Search; демонстрация недоступности материалов Platform |
| Наставник Platform | Дополнительно доступны материалы для наставника; полноценного кабинета согласования нет |
| Алекс / Сэм | Дополнительные тестовые пользователи Notifications/Payments с другими ресурсами для заявок |

Разграничение прав — обязательное требование. Красота списка профилей — улучшение UX. В настоящей интеграции роль приходит из авторизации; для прототипа достаточно демонстрационных пользователей и серверной проверки прав.

### Что важно для оценки

## Что уже работает и не требует переделки ради идеала
