# Бэкенд: первый срез

## Решение

Модульный монолит на Go с clean architecture внутри предметного модуля `access`.
Один процесс API владеет прикладным состоянием. Отдельный процесс `mock-access`
имитирует внешнюю корпоративную систему, он не является микросервисом продукта.
Go-модуль лежит в `../services`, чтобы позднее разместить фронтенд и Python
в том же репозитории без смешивания инструментов сборки.

Зависимости направлены внутрь:

```text
cmd/server: сборка зависимостей
    transport/httpapi → access/application → access/domain
    access/adapters/postgres → access/domain
    access/adapters/tickethttp → access/domain
    onboarding → access/domain (только проекция чтения)
```

`application` определяет интерфейсы Repository, Gateway, Policy, которые ему нужны.
Domain не импортирует HTTP, pgx, SQL, конфигурацию или AI. DTO находятся в HTTP-адаптерах.
В `cmd` зависимости собираются явно, без контейнера DI и глобальных сервисов.

## Границы модулей

- `access`: предложения заявок, подтверждение, отмена, повторная отправка,
  синхронизация и защита от дублей.
- `identity`: доверенный контекст пользователя. Текущий HTTP-адаптер сопоставляет
  два тестовых токена пользователям. Роль/владелец не принимаются из JSON.
- `onboarding`: проекция прогресса для каждой операции доступа. Пока это не полный
  план адаптации, нет отдельных задач с собственным CRUD и расписаниями.
- `platform`: конфигурация, запуск, подключение БД и миграции.
- `mocktickets`: отдельная имитация корпоративного API, владеющая схемой `mock_access`.

Новые предметные модули добавляем по готовым сценариям. Универсального движка
действий, пустых модулей чата, шины событий и универсального репозитория нет.

## Подтверждение и идемпотентность

Предложение неизменяемо: новые параметры требуют нового предложения и подтверждения.
Первое подтверждение проверяет его `version`. Повтор уже подтверждённой операции
возвращает сохранённое состояние, даже если версия в повторе устарела.

На входе `Idempotency-Key` уникален в пределах пользователя. В PostgreSQL действует
UNIQUE(owner_id,idempotency_key). Сервис заявок получает постоянный `request.ID`
как свой ключ операции. Создание внешней заявки обязано быть идемпотентным в том
числе при конкурентных вызовах и неопределённом результате предыдущего запроса.

Подтверждение блокирует строку (`SELECT FOR UPDATE`), проверяет права и фиксирует
`submitting`. Транзакция заканчивается **до** HTTP-вызова. Результат сохраняется
в следующей короткой транзакции. Изменение заявки и запись аудита атомарны.
Запоздавший `pending` не откатывает `granted` или `rejected`.

При тайм-ауте результат остаётся неопределённым. Если контекст уже отменён и запись
`unknown` не удалась, сохранится `submitting`; оба состояния восстанавливаются
через `/refresh`. Сначала выполняется Lookup. Если сервис достоверно вернул 404,
допускается Create с **тем же** ключом и повторной проверкой текущих прав.
Нет обещания exactly-once без соответствующего контракта внешнего сервиса.

`GET` не выполняет внешних действий. `POST /refresh` может безопасно повторить
ранее подтверждённую отправку. Фоновый reconciliation worker пока не реализован:
восстановление запускается явно. При интеграции фронтенд сможет вызывать refresh
с ограниченным polling или эту работу возьмёт серверный worker.

## Хранение

`access_requests`: идентификатор, владелец, ключ идемпотентности и JSONB агрегата.
JSONB выбран для небольшого первого среза без аналитических выборок по полям.
Репозиторий отвечает за его сериализацию. Если потребуются фильтрация по статусам,
массовый поиск задач или worker, добавим явные колонки и индексы отдельной миграцией.
Это осознанный компромисс текущей реализации, не универсальный шаблон хранения.

`access_events`: журнал переходов с версией и состоянием внешней заявки.
Это аудит изменения состояния, а не полный журнал всех попыток обращения.

`mock_access.tickets`: независимый источник внешних ID и статусов. Для удобства
локального запуска используется тот же PostgreSQL, но отдельная схема. В реальной
интеграции бэкенд не получит доступ к хранилищу внешнего сервиса.

Миграция v1 встроена в бинарник и отмечается в `schema_migrations`. Уже применённый
SQL не изменяем при развитии: следующая правка схемы должна стать миграцией v2.

## Что подключим позже

Фронтенд использует существующие HTTP use cases. Для AI предложение действия будет
поступать в `Propose`, а подтверждение останется отдельным пользовательским вызовом.
Доверенный Actor берётся из серверного контекста. Поиск, документы, диалоги,
источники и SDD поведения самой модели будут отдельной работой вместе с AI-разработчиком.

Текущие ограничения: синтетическая политика прав, отсутствие пагинации списка,
отсутствие автоматического восстановления в фоне, отсутствие ограничения числа
разных заявок на один ресурс. Перед внешним развёртыванием нужны корпоративная
аутентификация, политика доступа и эксплуатационные ограничения.
